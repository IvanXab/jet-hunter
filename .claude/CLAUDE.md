# jet-hunter

Turborepo-монорепозиторий на npm workspaces. В `apps/` лежит frontend на React 19
+ Vite, в `packages/` — общие конфиги и UI-kit на React 19 + Tailwind 4.

## Окружение

- Node строго **24.14.0**. Версия зафиксирована в `.nvmrc`, `engines.node` и
  `.npmrc` (`engine-strict=true`). Перед любыми командами: `nvm use`.
- Пакетный менеджер — **npm** (workspaces). Не использовать pnpm/yarn/bun.
- Remote cache Turborepo **отключён** (`remoteCache.enabled: false` в `turbo.json`).
  Не выполнять `turbo login` / `turbo link` и не включать его без явной просьбы.

## Структура

```
apps/                        — приложения (Next.js, API, CLI и т.п.)
apps/frontend/               — SPA на React 19 + React Compiler + Vite (@repo/frontend)
packages/                    — внутренние пакеты (@repo/*)
packages/typescript-config/  — общий tsconfig
packages/eslint-config/      — общий eslint
packages/tailwind-config/    — тема Tailwind (@theme с токенами дизайна)
packages/ui/                 — UI-kit на React 19 (@repo/ui)
turbo.json                   — граф задач
```

### Подключение общих конфигов

Каждый новый пакет наследует их, а не заводит свои правила:

```jsonc
// tsconfig.json
{
  "extends": "@repo/typescript-config/base.json", // или node.json / react.json
  "include": ["src/**/*.ts"],
}
```

```js
// eslint.config.js
import { config } from "@repo/eslint-config/base"; // для React — /react
export default config;
```

```jsonc
// package.json
{
  "devDependencies": {
    "@repo/eslint-config": "*",
    "@repo/typescript-config": "*",
  },
  "scripts": {
    "lint": "eslint .",
    "check-types": "tsc --noEmit",
  },
}
```

Правила из «Правил написания кода» ниже по большей части уже включены в
`@repo/eslint-config` — отключать их в конкретном пакете нельзя без причины,
записанной рядом в комментарии.

## Задачи

Задачи живут в `package.json` каждого пакета. Корневой `package.json` только
делегирует в `turbo run <task>` — никакой логики сборки в корне.

Зарегистрированные задачи: `build`, `dev`, `lint`, `check-types`, `test`.
`lint` и `check-types` зависят от transit-ноды `transit`, чтобы выполняться
параллельно, но корректно инвалидировать кеш при изменении зависимостей.

В скриптах и CI всегда писать `turbo run <task>`, а не короткую форму `turbo <task>`.

## Правила при добавлении кода

- Новое приложение → `apps/<name>`, новый общий код → `packages/<name>`.
  Не держать shared-код внутри приложения.
- Импорты между пакетами только через имя пакета (`@repo/ui`), не через
  относительные пути в чужую директорию.
- Зависимость между пакетами объявляется в `package.json` (`"@repo/x": "*"`),
  иначе `dependsOn: ["^build"]` не отработает. Не писать `prebuild`-скрипты,
  вручную собирающие соседей.
- Для задачи, которая пишет файлы, обязательно указывать `outputs` в `turbo.json`,
  иначе кеш не восстановит результат.
- Переменные окружения, влияющие на сборку, перечислять в `env` / `globalEnv`.
- `.env` держать в пакетах, которым он нужен, а не в корне репозитория.
- В корневые зависимости ставить только инструменты репозитория (turbo, prettier).
  Зависимости приложений — в их собственные `package.json`.

## Правила написания кода

Язык — TypeScript. JavaScript-файлы в `src/` не создавать.

### Типы

- `strict: true` во всех `tsconfig.json`. Не отключать отдельные strict-флаги
  в конкретном пакете, чтобы «починить» ошибку.
- `any` запрещён. Если тип неизвестен — `unknown` с последующим сужением.
  `as` использовать только там, где сужение невозможно выразить иначе,
  и рядом объяснять почему.
- `@ts-ignore` не использовать; в исключительном случае — `@ts-expect-error`
  с комментарием-причиной (он сам станет ошибкой, когда проблема исчезнет).
- Типы выводить, а не дублировать: аннотировать границы (параметры, возвращаемые
  значения экспортируемых функций), внутри — полагаться на вывод.
- Для наборов значений — union строковых литералов, а не `enum`.
- Предпочитать `type` для union/пересечений, `interface` — для объектов,
  которые расширяются.

### Границы пакета

- У каждого пакета явный `exports` в `package.json`. Всё, что не в `exports`, —
  внутренняя реализация, импортировать снаружи нельзя.
- Публичный API пакета собирать в `src/index.ts`, без `export *` из внутренних
  модулей вразнобой.
- Не использовать default-экспорты, кроме случаев, где их требует фреймворк
  (страницы Next.js, конфиги). Именованные экспорты переименовываются
  предсказуемо и лучше автоимпортятся.

### Ошибки

- Не глотать ошибки: пустой `catch` или `catch { return null }` без причины —
  запрещено.
- Кидать `Error` (или наследника), не строки и не объекты.
- Ожидаемые доменные сбои (не найдено, невалидный ввод) выражать в типе
  результата, а не исключением. Исключения — для действительно исключительного.
- Любые внешние данные (сеть, файлы, env, ввод пользователя) валидировать
  на границе, а не приводить типом.

### Асинхронность

- `async/await`, не цепочки `.then()`.
- Не терять промисы: каждый await'ится или явно обрабатывается.
- Независимые операции запускать через `Promise.all`, а не последовательными
  `await` в цикле.

### Стиль

- Именование: `camelCase` для переменных и функций, `PascalCase` для типов и
  классов, `SCREAMING_SNAKE_CASE` для констант-литералов. Файлы — `kebab-case`.
- Имена по смыслу, без сокращений (`user`, не `u`; `response`, не `res`,
  кроме привычных сигнатур middleware).
- Ранний возврат вместо глубокой вложенности. Больше трёх уровней — выносить
  в функцию.
- Импорты идут сплошным блоком без пустых строк между ними. Одна пустая
  строка — только после последнего импорта, чтобы отделить их от кода.
- Форматирование — Prettier (`npm run format`), вручную стиль не править и
  не спорить с ним.

### Комментарии

**Код не должен содержать комментариев.** Не писать их и не оставлять в коде,
который правите.

Комментарий — сигнал, что код непонятен сам по себе. Вместо него: осмысленное
имя, выделенная функция с говорящим названием, именованная промежуточная
переменная вместо сложного выражения, тип, выражающий ограничение.

Закомментированный код не коммитить — для этого есть git.

Единственные исключения, и они обязательны:

- описание при `@ts-expect-error` — без него линтер выдаст ошибку;
- причина при `eslint-disable` — иначе непонятно, почему правило снято;
- заголовки лицензий и пометки в сгенерированных файлах.

Это не относится к текстам вне кода: README, документы в `.docs/` и этот файл
пишутся словами и подробно.

### Чего не делать

- Не добавлять зависимость ради того, что решается несколькими строками.
- Не писать абстракции «на будущее» под один вызов.
- Не менять публичный API пакета мимоходом, попутно с другой задачей.

## Документация

Человеческая документация — в `.docs/`, точка входа — корневой `README.md`.
Изменили поведение, описанное в документе, — правьте документ в той же задаче.
Мелкое дополнение вставлять в существующий файл, а не заводить новый.

- `.docs/setup.md` — окружение, установка, типовые проблемы
- `.docs/monorepo.md` — структура, добавление пакетов, общие конфиги
- `.docs/turborepo.md` — граф задач, кеш, фильтры, CI

## Фронтенд

- UI — React 19. Компоненты из `@repo/ui`, не переписывать их копию в приложении.
- Стили — Tailwind 4. Конфигурация только в CSS (`@theme`), `tailwind.config.js`
  не заводить.
- Цвета, размеры и трекинг брать именами токенов из `@repo/tailwind-config`
  (`bg-canvas`, `text-ink-muted`, `border-line`, `text-control`,
  `tracking-label`). Литералы вида `text-[#1a150f]` и `p-[13px]` — только там,
  где в дизайне действительно нет токена.
- Классы Tailwind писать в разметке целиком: `` `text-${tone}` `` в сборку не
  попадёт, варианты раскладывать в `Record<Тип, string>`.
- Новый компонент кита → `packages/ui/src/<component>/<component>.tsx` плюс
  экспорт в `src/index.ts`. Отдельных CSS-файлов у компонентов нет.
